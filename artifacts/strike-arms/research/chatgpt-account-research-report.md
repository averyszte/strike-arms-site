# Functionality (Customer Account Features)  
A modern B2C account portal should include: user registration/login, profile management, order history, address book, and preference controls. **Must-have:** a secure signup/login system (email/password) with logout, email verification (optional but recommended), and password reset. Supabase Auth covers these out of the box (email signup/sign-in, optional email confirmation, and built-in reset flow).  *(Nice-to-have:* social/OAuth login – Supabase supports many providers (Google, GitHub, etc.), which can simplify login and improve UX, but for a small retailer it’s optional.)* 

Customers should manage their profile: view/edit personal details (name, contact, password). A profile page with an **editable** name/email/phone is expected (profile editing is “must-have” for any account). Many e‑commerce guides note accounts should allow updating contact info and shipping details.  Similarly, a **saved addresses** feature is essential: users often need multiple shipping addresses, so a directory of editable addresses is highly recommended. (Billing addresses are less critical since Stripe Checkout collects payment info, but storing default billing details can speed repeat buys.) 

An **order history** is a must: after checkout, customers expect to see past orders and statuses. Even though Stripe Checkout handles payments, the site should record completed orders (e.g. via Stripe webhooks) so users can view order number, date, items and totals. This fosters trust and repeat business. 

**Marketing and privacy preferences** should be user-editable. Allow users to opt in/out of newsletters and promotional emails.  Accounts should let them update subscription choices (since GDPR requires withdrawable consent). This is legally important (see next section). 

**Session management:** include logout on the account page. Supabase’s sign-out already revokes all sessions for that user, so a single “Log out” button suffices (it ends “all devices” by default). It’s wise to show active sessions or last login time for transparency (a best practice). 

**Security settings:** consider offering password change (via old/new or reset link) and 2FA/MFA toggling in account settings. MFA/2FA is *highly recommended* as a best practice. Supabase Auth supports user-enrolled MFA (TOTP or SMS). While not mandatory, enabling MFA greatly reduces account-takeover risk. For a small retailer it can be optional (e.g. advanced setting), but offering it follows security best practices.  

**Guest checkout vs account creation:** Research shows forcing sign-up causes ~19% of shoppers to abandon carts. Best practice is to allow **guest checkout** (collect only shipping/payment info, no account required) and then prompt optional account creation afterwards (e.g. “Create an account with this info?”). This maximizes first-time conversions. (Accounts are more valuable for repeat buyers, but for initial sale guest flow is recommended.) This strategy doesn’t affect GDPR requirements: if you hold personal data from a guest (e.g. name, address, email for the sale), the same data protection obligations apply regardless of guest vs account user. 

**Feature summary:** Must-have features for launch include registration/login (with email verify and password reset), editable profile and addresses, order history, marketing opt-out controls, and logout. Nice-to-have features include social login, wishlists, saved payment methods, and advanced session views. Supabase Auth provides the core auth flows (email/password signup/login, email verification, reset); everything else (profiles, addresses, orders, wishlist, preferences) will need custom tables or additional logic built on Supabase/Postgres. 

# Legal & Compliance (Ireland and EU Privacy Law)  
**Privacy notice (Art.13 GDPR):** Legally, you must inform users about data use *at registration*. Article 13 requires giving privacy information “at the time when personal data are obtained”. Practically, link to a privacy policy (detailing what data is collected, legal basis, retention, rights, etc.) on the signup page. This is a strict requirement – failure to do so is non-compliant. 

**Lawful basis:** Most account processing (collecting names, addresses, processing orders) can be justified as *performance of a contract* (Art.6(1)(b) GDPR): necessary to fulfill the sale. Marketing emails require either explicit *consent* (Art.6(1)(a)) or use of the ePrivacy “soft opt-in” rule. Under Ireland’s ePrivacy Regulations, you may send promotional emails to existing customers without separate consent if (a) they bought from you, (b) you only market similar products, (c) they were given an opt-out at purchase, and (d) it’s within 12 months. This is a legally accepted “soft opt-in” (Reg.13(11) ePrivacy). For any marketing beyond this (or to non-customers), you need explicit opt-in consent. All consents taken must be **documented and easily withdrawable**. In practice, add clear checkboxes (not pre-ticked) and log the fact/time of consent. Provide an easy way to unsubscribe (GDPR requires withdrawal be as easy as giving consent). 

**Right to erasure (“delete my account,” Art.17 GDPR):** Data subjects have a legal right to request deletion of their personal data. However, delete-right is *not absolute*: you must retain data that is legally required. For example, Irish law (Companies Act 2014) mandates retaining accounting/sales records for **6 years**. Thus, when a user requests account deletion, you should delete or anonymise all personal identifiers (name, email, etc.), but you may legitimately keep the bare transaction records for tax/audit (with personal details removed). A common approach is to “anonymise” order records (e.g. replace name with pseudonym, remove contact) and mark account as closed. That way you honour erasure of **personal** data while preserving necessary records. GDPR Recital 65 and Art.17 exclude data kept for compliance with legal obligations, so this is acceptable. 

   – *Self-service delete button:* The GDPR does not mandate a particular UI for erasure requests. It is legally sufficient to process a written request promptly. A one-click “Delete Account” button is not required by law, but is consumer-friendly. Many sites offer it as best practice, but you can also handle requests by email or form. The key is timely compliance (within one month of request). 

**Right of access (Art.15) & portability (Art.20):** GDPR grants users the right to a copy of their data and, in certain cases, a machine-readable export (if processing is by automated means and based on consent or contract). In practice, it’s *required* to comply if asked, but you are not obligated to proactively offer an automated download feature. You should be prepared to provide, on request, all personal data held about the user (name, email, addresses, order history, preferences, etc.), and ideally in a structured electronic format (PDF/CSV/JSON). Offering a “Download my data” button is **good practice** and can improve trust, but legally you could also fulfill requests via email. The easiest compliance path is to compile data from your database and email it. 

**Data minimisation & retention:** GDPR’s principle of minimisation requires collecting only data necessary for the purpose. For a retailer, this means avoid extraneous PII (e.g. don’t collect ID numbers unless needed). Store only what supports orders and legal needs: name, email, shipping address, purchase history, etc. Do *not* store full credit-card details (Stripe handles payments so card data isn’t stored on your servers). Regarding retention, keep personal data only as long as needed (Art.5(1)(e) “storage limitation”). Practically, keep account/order data for at least the legally required 6 years, then anonymise or delete. Marketing lists should be regularly cleaned of inactive contacts. 

**Cookies and tracking (ePrivacy):** Irish/EU law requires consent for most cookies. Strictly necessary cookies (e.g. session cookie for logged-in state, shopping cart contents) are *exempt* from consent, since they enable a requested service. But all other cookies/trackers (analytics, advertising, persistent preference cookies, etc.) require explicit opt-in consent under ePrivacy Regs. DPC guidance is clear: you must obtain consent before setting non-essential cookies. In practice, implement a cookie-banner that lets users accept or reject all non-essential cookies. You may allow “continued use” as consent only if it is as clear as clicking “Accept” (Irish DPC advises a clear affirmative action). Ensure your banner details cookie categories. Use a well-known solution to manage this. 

**Data breach notifications:** Under GDPR Articles 33–34, you must *notify the Data Protection Commission (DPC)* of a reportable breach within 72 hours of becoming aware (unless the breach is unlikely to risk individuals). If the breach poses **high risk to rights/freedoms** (e.g. theft of emails+passwords, or credit card data), you must also notify affected individuals without undue delay. Even a small retailer should have an incident response plan: define who will investigate breaches, when to notify DPC, and prepare sample breach notification content. In practice, any compromise of the customer database or credentials should trigger a notification to DPC (and possibly emails to users advising password reset). Document everything to demonstrate compliance. 

**Age considerations:** The GDPR sets a digital consent age of 16 (Irish Data Protection Act 2018). This means users **under 16** cannot validly consent to data processing (including creating an account) without parental approval. It is safest to restrict signups to 16+ (explicitly or implicitly); if you allow teens (13–15), you must verify parental consent (complex to implement). For airsoft sales specifically, Irish law classifies airguns over 1 joule as firearms, so there may be separate age restrictions (often 18+) under firearms legislation. This is outside GDPR but crucial for the business: we do **not** adjudicate it here, but flag that any age check for airsoft must follow the Firearms Acts (e.g. Criminal Justice Act 2006 and subsequent regulations). We assume only adults should complete purchases of powered airsoft; implement an age-confirmation step at checkout or require account birthdate (with parental consent if under 18). Because this is legal territory, consult an Irish solicitor or the DPC’s guidance on marketing to minors rather than guessing. 

# Security Best Practices  
**Password policy:** Follow current NIST/OWASP guidance. Require a minimum length (e.g. 8 characters at least, with advice to use a longer passphrase). **Do not** enforce arbitrary complexity rules (no forced symbols or caps), as that has been discouraged by NIST. Instead *check passwords against breached-password lists*: for example, use the “Have I Been Pwned” API to reject known compromised passwords. This is strongly recommended. Use a password strength meter (e.g. zxcvbn) to guide users, but do not block creative passphrases. Encourage users to use long, memorable passwords. There is no need for periodic password resets by policy (NIST says avoid forced expiration); only force a change if there is evidence of compromise or at user request. 

**Multi-Factor Authentication (MFA):** Offer MFA (2FA) to customers. Supabase supports optional user-enabled MFA via TOTP apps or SMS. It’s best practice (though not required) to allow or require MFA, especially for account-sensitive actions (viewing payment data, making changes). At minimum, design the account UI to let users *add/remove* a second factor. Supabase Auth provides APIs for enrolling factors and checking them. Use the `aal` claim (authentication-assurance level) in the JWT to enforce access (e.g. require `aal2` for high-value actions). If implementing, ensure the MFA enrollment flow is user-friendly (show QR code, backup codes, etc.). 

**Session and token handling:** As a React SPA, you’ll store the Supabase JWT in the browser. Avoid XSS attacks by securing where tokens live. If using a public frontend (Cloudflare Pages), consider using HttpOnly secure cookies (Supabase can be configured to issue cookies) so that JS cannot read tokens. If you must use `localStorage` or `sessionStorage` (e.g. using `createClient()`), ensure your app is hardened against XSS (use a strict Content Security Policy, sanitize inputs, audit third-party scripts). Supabase renews JWTs regularly: default access tokens expire in 1 hour. This is reasonable; do not set extremely long lifetimes. For higher security, you can shorten JWT expiry and require re-login (or enforce refresh) more often. Supabase also offers session lifetime settings (in Pro plans) for time-boxed or inactive sessions – use those to auto-expire stale logins. 

**Supabase-specific security:** Enable Row-Level Security (RLS) on your tables to ensure users can only access their own data (e.g. orders, profile). Supabase’s RLS plus JWT `sub` claim lets you write policies so only the user’s `uid` can read their rows. For example, an `orders` table should include a `user_id` column (the Supabase user UID) and an RLS policy enforcing `user_id = auth.uid()`. This prevents any leakage of one user’s data to another. Also rotate your Supabase JWT signing keys periodically using the dashboard (the “Signing keys” system) for better security. Supabase recommends using asymmetric signing keys (RSA/ECDSA) rather than the legacy shared secret, as it improves key rotation and security. 

**Cloudflare Pages considerations:** Since the frontend is static, most logic is in the browser. Still, leverage Cloudflare’s protections: enable WAF rules to block common attacks, use Cloudflare’s rate-limiting (especially on auth endpoints), and ensure HTTPS is enforced. On the SPA, set strict HTTP headers (e.g. `Content-Security-Policy`, `X-Frame-Options`) via Cloudflare or meta tags to mitigate XSS. If using any Cloudflare Workers or edge logic, treat them like part of your backend with secrets in Cloudflare’s environment variables (don’t expose API keys to the client). 

**Brute-force and abuse protection:** Supabase Auth has built-in rate limiting on sign-in and signup endpoints. You should configure reasonable limits (e.g. a few attempts per minute per IP or account). OWASP recommends account lockout or throttling after repeated failed logins. For example, after 5 failed attempts on one account, temporarily block further attempts or require a captcha. Importantly, tie attempts to the user account (not just IP), to prevent an attacker from locking out others easily. Log all failed logins and lockout events for monitoring. Optionally, integrate a CAPTCHA on the login page after several failures to slow bots. Also consider notifying users on suspicious activity (e.g. email a login alert when an account is accessed from a new device). 

**Account takeover mitigation:** Besides the above, use HTTPS everywhere (Cloudflare provides TLS by default), and never log sensitive tokens. For password recovery, use time-limited one-click reset links sent to the user’s verified email (Supabase offers this flow). If a reset link is used, revoke any existing sessions. Also consider “Login notifications”: Supabase can send a “NEW LOGIN” email (if configured) or you can implement an alert so users know if their account was used. 

**Stripe/checkout security:** Using Stripe Checkout offloads PCI scope. Ensure you handle Stripe webhooks securely: verify the webhook signature (using Stripe’s secret) to confirm events come from Stripe. Do **not** trust incoming webhook data blindly. Store only the minimal Stripe identifiers (payment intent ID, customer ID) and use Stripe’s API to fetch details as needed. Never store full credit card numbers or CVVs – Stripe will not send these. For orders, record only what’s needed (product, amount, date). 

# Prioritised Build Checklist  

**Must-have for launch (Legal requirements in **bold**):**  
- **Privacy notice at signup** (show link to policy) – *LEGALLY REQUIRED* (GDPR Art13).  
- **Signup/Login** (email+password flow with email verification, logout, password reset).  
- Profile page with **editable contact info** (name/email/phone) – must allow corrections.  
- **One or more saved shipping addresses** per user.  
- **Order history** listing past orders (ID, date, status, items).  
- **Email marketing preferences** toggle (opt-in/opt-out) – required for GDPR compliance.  
- **Cookie consent banner** covering non-essential cookies (e.g. analytics).  
- Basic **session management**: logout button (Supabase’s logout revokes all sessions).  
- **Ability to delete or anonymise account on request** (comply with Art.17 erasure). If “Delete Account” button is provided, it should wipe personal data except legally required records. (If not automated, ensure a manual workflow to handle user deletion requests within 30 days.)  
- **Data export** on request: have a process to email user’s data (login, address, orders, preferences) as PDF/CSV/JSON if asked (Art.15/20). *(Best practice: provide “Download Data” option in profile.)*  
- Age check: block sign-ups under 16 or require parental consent (*Digital consent age*). (For airsoft products, add an age-confirmation step at checkout; consult legal advice on firearm age rules.)  

**Should-have by launch (Best practice/security, if time allows):**  
- **Secure password policy:** enforce minimum length (≥8), no forced complexity, and breach-list check.  
- MFA opt-in: let users enable 2FA via TOTP or SMS. (If feasible, at least allow optional MFA setup.)  
- **Session expiry:** ensure JWT expiry is not excessively long (Supabase default 1h is fine). Consider single-session enforcement or inactivity timeouts in Supabase settings (Pro feature).  
- Wishlist (saved items) and “save for later” features (enhance UX, not legally required).  
- Social login (Google/Facebook/etc) for convenience, if alignment with user base.  
- Account/session overview (show last login time, active sessions) in profile for transparency.  
- Logout-from-all-devices (Supabase’s logout already does this). If needed, clarify in UI that “Logout” ends all sessions.  
- ReCAPTCHA or similar on signup/login to deter bots (Supabase has CAPTCHA integration).  
- Content Security Policy and rate-limits on login APIs.  
- Logging/monitoring of auth events (follow OWASP guidance: log all failures).  
- **Backup & incident plan:** Prepare a breach response plan (contacts, DPC form, email templates). This is a GDPR best practice (Art.33), though not a “feature.”  

**Later / optional:**  
- Analytics opt-in (to track usage, separate from cookie consent UI).  
- Gamification of accounts (loyalty, reviews).  
- In-app purchase history filtering or recurring order features.  
- Integration of external auth providers (GitHub, Apple ID).  
- Progressive Web App features (not account-related).  

Every **legal obligation** above (GDPR rights, cookie consent, age limit) is marked *LEGALLY REQUIRED*. Meeting these is non-negotiable. The others are best practices to improve security and user experience.
